# 更新器修复设计（第一阶段）

> 前置约束（来自需求方）：
> 1. 这是**通用更新器**，将复用到新老项目，修复不得绑死任何业务/仓库。
> 2. **不做代码签名**（既定前提）。不得把"加签名"作为建议或验收条件；也不得因为无签名而放松任何校验（feed 签名可配、sha256 必校验、HTTPS 必用）。
> 3. 无签名发行下，更新流程**不能新增杀软误报面**：不在运行中自覆盖、不在临时目录落可执行文件、重启/替换时序要常规、进程链要简单。

## 1. 事务模型（P0：BUG-01/02/04/05）

### 1.1 journal v2

`JournalEntry` 从 `{target, backup}` 扩展为：

```jsonc
{
  "target": "C:\\App\\app.exe",
  "backup": "C:\\...\\backup\\app.exe",   // 原文件不存在时为 null
  "action": "write",                       // write | delete
  "renamed_from_running": false            // 仅当目标是运行中的更新器自身
}
```

- `action=delete`：上一版有、新版没有的文件。安装时**移动到** `backup/__deleted__/<rel>`，而不是直接删除；这样回滚可以恢复。
- `renamed_from_running`：记录"目标曾被改名为 `*.old-<pid>`"，重试时不再重复改名。

### 1.2 安装两段式（幂等）

```
A. 计划
   - 若存在同版本、未提交的 journal → 直接复用它（不再重新规划，避免把新文件当旧文件备份）
   - 否则：规划 write 项 + delete 项，先落 journal（committed=false），再动文件
B. 执行（每一步都可重复执行）
   - write：backup 不存在且 target 存在 → copy target → backup
            rename_from_running 且 backup 不存在且 target 存在 → rename target → .old-<pid>
            copy staging → target（覆盖）
   - delete：backup 不存在 → rename target → backup/__deleted__/<rel>
              backup 已存在 → 删除残留 target
   - 写清单 → journal.committed = true
```

重试（`retry_until`）复用同一份 journal，因此第二轮不会重新判定"target 是否存在"，备份不会被新文件覆盖。

### 1.3 回滚（journal 驱动）

- 遍历 journal entries：
  - `write` + backup 存在 → 还原；backup 为 null → 删除 target
  - `delete` + backup 存在 → 还原
- 目标若是**当前运行中的镜像** → 先 rename 成 `.old-<pid>`，再 copy 备份回去（不在运行中覆盖自己）。
- 任一还原失败 → 返回错误，**保留 backup 与 journal**，不得清理。
- 全部成功 → 删除 journal，再清理 `*.old-*`（跳过当前运行镜像）。

### 1.4 recover 顺序（BUG-01 的根因修复）

```
读 journal
├ 不存在 → 清理 *.old-*（跳过运行镜像）→ Clean
├ committed → 删 journal → 清理 *.old-*（跳过运行镜像）→ Committed
└ 未提交 → 先回滚
     ├ 成功 → 删 journal → 清理 *.old-* → RolledBack(n)
     └ 失败 → 保留 journal + backup，返回错误（下次继续尝试，不能删证据）
```

`cleanup_old_images` 永远不会在"回滚完成前"执行，因此不会删掉 journal 要用的备份。

## 2. apply 失败路径（P0：BUG-03）

统一规则：**进入 apply 后，任何失败出口都尝试拉起一次旧版**（`relaunch(cfg)`），包括：

- install 失败（含 90s 重试用尽）
- 新版拉起失败
- 3s 启动探测失败（回滚后拉起）
- 目录不可写且已提权
- UAC 被拒
- pending 丢失

拉起前先确保 `exe_name` 存在；拉起失败只记录，不再递归。

## 3. 跨进程锁（P0：BUG-06）

新增 `src/lock.rs`：

- 锁文件：`<cache>/updater.lock`，内容 `"<pid> <unix_ts>"`，`create_new` 原子创建。
- 获取失败：读 pid/ts → 进程已退出或 ts 超过 15 分钟 → 视为陈旧锁，删除后重试；否则每 200ms 重试，最多 10s，超时报"另一个更新进程正在运行"。
- 覆盖范围：check / download / apply / recover / clean / skip / unskip（verify-feed 不取锁）。
- Drop 时删除锁文件（删除失败忽略）。
- 提权重启时原进程立即退出，提权进程通过"pid 已死"识别陈旧锁；UAC 等待期间不会死锁。

## 4. 协议输出（P0：BUG-24）

`protocol::emit` 改为 `writeln!(stdout().lock(), ...)`，**忽略写入错误**；序列化失败降级为纯文本行，同样忽略错误。禁止 `println!` 的 panic 行为。

## 5. 下载（P1：BUG-09）

- 客户端：`connect_timeout(15s)` + 总超时 30 分钟；`http_text` 单请求 `timeout(30s)`。
- `.part` 已存在 → `Range: bytes=<len>-`：
  - `206` → 追加写
  - `200` → 服务端不支持续传，截断重下
  - `416` → 删除 `.part` 重下
- 最多 3 次尝试，退避 1s/2s；每次失败保留 `.part`，下次续传。
- 完成后按最终文件整文件 SHA256 校验（不再边下边算，续传也正确），大小不符则删除 `.part`。
- 进度帧的 `received` 包含已续传的前缀。

## 6. UAC 换账户（P1：BUG-10）

- 新增 CLI `--cache <abs-dir>`，`Config` 增加 `cache_override`，`cache_dir()` 优先返回它。
- UAC 重启自身时，把 `--cache <当前 cache>` 追加进参数，提权进程不再依赖 `LOCALAPPDATA`。
- 校验必须是绝对路径；拒绝相对路径。

## 7. `--skip` 取消（P1：BUG-07）

- 新增 `--unskip`：清空 `skipped_version` 并保存。
- GUI：
  - 记录 `gState.skipped`（由 `Available.skipped` 更新；`Idle` 时清空）。
  - 按钮文案：未跳过 → "跳过此版本"；已跳过 → "取消跳过"。
  - 提示语："版本 X 已被跳过，点「取消跳过」恢复提示"。
  - 点击后执行对应命令，再自动做一次手动检查刷新界面。

## 8. 脚手架 / CI 一致性（P1：BUG-08）

`build.yml` 不再硬编码 `windows-x64` / `portable` / `latest-version-*.json`：

- 从 `updater.conf` 读取 `platform`、`variant`、`product`、`feed_name`、`exe_name`。
- `platform` → target triple（`windows-x64 → x86_64-pc-windows-msvc`，`windows-arm64 → aarch64-pc-windows-msvc`；未知平台直接失败）。
- zip 名、feed 内容、feed 文件名、签名路径全部用上面读到的值。
- 脚手架生成的 `feed_name=latest-version-<platform>.json` 与 CI 一致。

## 9. 无签名前提下的杀软时序约束（实现检查清单）

- 不在运行中覆盖自身：安装与回滚都走"rename → 写新文件"。
- 可执行文件只落在安装目录与 `%LOCALAPPDATA%\GenericUpdater`，**不落 `%TEMP%`**。
- 进程链保持 `主程序 → 更新器 → 新主程序`，不引入 `cmd /c`、`powershell -c`、计划任务、服务。
- `*.old-<pid>` 延迟到下次启动清理，不在安装完成瞬间强删运行镜像。
- 更新器保持 GUI 子系统（无控制台窗口）。
