# 更新功能说明

> 面向开发/维护者：讲清"它是什么、怎么工作、为什么这么设计"。
> 接入步骤见 [02-接入指南.md](02-接入指南.md)，历次决策见 [03-设计决策记录.md](03-设计决策记录.md)。

## 1. 目标

给 Windows 桌面程序加一套可复用的自动更新能力：

- **用户侧**：启动后延迟检查、手动刷新、进度条、变更日志、跳过版本、重启完成；
- **工程侧**：更新器独立进程，任何语言的主程序都能接；配置编译期固化，发布只有一个 exe；
- **安全侧**：RSA-PSS 元数据签名、包 SHA256、固定下载源、失败/断电回滚；
- **运维侧**：CI 一条龙出包，密钥只配一次，版本只由 tag 决定。

## 2. 组成

```
┌─────────────────────┐   stdout JSON 帧     ┌───────────────────────┐
│  客户端 GUI (C++)   │ ───────────────────► │  更新器 (Rust)         │
│  按钮/进度/更新日志  │ ◄─────────────────── │  检查/验签/下载/安装    │
└─────────────────────┘                      └──────────┬────────────┘
                                                        │ GitHub Release
                                                        ▼
                                     latest-version-windows-x64.json（签名信封）
                                     <product>-<version>-windows-x64-portable.zip
                                     <...>.zip.sha256
```

| 部分 | 职责 |
|---|---|
| `generic-updater.exe` | 唯一有权做网络、验签、写文件、拉起新版的进程 |
| 客户端 GUI | 只做界面与进程协调，不碰网络和安装 |
| feed | 一次发布的完整契约，整体签名 |
| CI | 编译两端 → 打包 → 算哈希 → 签名 → 出 Release |

GUI 与更新器之间没有 DLL/静态库耦合，只有 **stdout 一行一条 JSON** 的协议，所以主程序可以用任何语言写。

## 3. 版本与命名

- **版本只由 tag 决定**：`v0.6.0` → `0.6.0`；`v1.5.7_snow-shot` → `1.5.7`（`_` 后丢弃）。
- `Cargo.toml` 的 version 只是工具自身编号，不参与发布。
- 资产命名：

```
latest-version-windows-x64.json
<product>-<version>-windows-x64-portable.zip
<product>-<version>-windows-x64-portable.zip.sha256
```

多平台再加 `latest-version-windows-arm64.json`，客户端只认自己那份。

## 4. 配置（编译期固化）

`updater.conf` 是唯一配置源：

```ini
repo=owner/repo
feed_name=latest-version-windows-x64.json
exe_name=MyApp.exe            # 更新后要拉起的程序（不是更新器自己）
homepage=https://...
variant=portable              # portable / online / offline
platform=windows-x64
interval_hours=24             # 自动检查最小间隔
startup_check_delay_seconds=30 # 界面显示后延迟多久再检查
product=my-app                # 必须与 feed.product 一致
window_title=MyApp — 版本更新
require_signature=true        # 是否强制验签
```

构建时：

- Rust：`build.rs` 生成常量编进 `generic-updater.exe`；
- C++：`scripts/gen-app-config.ps1` 生成 `client/build-config.h` 编进 GUI（含 `APP_BUILD_VERSION`、`APP_STARTUP_DELAY_SECONDS`）。

因此**发布包只有一个 exe + version.txt**，没有 ini，用户改不了也丢不了。
调试时可用 `--config xxx.json` 或 `UPDATER_CONFIG` 环境变量覆盖。

## 5. 检查机制

| 场景 | 行为 |
|---|---|
| 启动自动检查 | 界面显示后延迟 `startup_check_delay_seconds`（默认 30s），再判断 24h 间隔 |
| 24h 内再次打开 | 不联网，但用缓存结果提示"有更新"（不会假报"已是最新"） |
| 手动「检查更新」 | 无视延迟与间隔，立即联网 |
| 检查失败 | 不刷新时间戳，下次启动重试 |
| 用户跳过某版本 | 记进 `state.json`，仍提示有更新但标注「已跳过」并禁用安装 |

`state.json`（缓存目录）字段：

```
last_check_unix        上次成功检查时间
last_remote_version    上次查到的远端版本（24h 内用它提示）
last_remote_notes/size 更新日志与包大小缓存
skipped_version        用户跳过的版本
pending_*              已下载待安装的版本/暂存路径
```

检查前会先执行一次事务恢复（`journal::recover`），保证不会在"半个新版本"上继续。

## 6. 状态机与协议

stdout 一行一条 JSON：

```json
{"protocol":2,"type":"status","state":"Available","version":"0.6.0",
 "notes":"…","received":0,"total":1212762,"error":null,
 "automatic":true,"skipped":false}
```

状态：`Unavailable / Idle / Checking / Available / Downloading / Verifying /
Ready / Applying / Failed`（与 snow-shot 的 `UpdateState` 对齐）。

- `automatic`：自动还是手动检查；
- `skipped`：该版本是否被跳过；
- `received/total`：下载进度；`Available` 的 `total` 就是包大小。

## 7. 更新流程

```
--download：Checking → Available → Downloading → Verifying → Ready
--apply   ：Applying → 备份/覆盖/删旧 → 拉起新版 → 3 秒存活探测 → Ready
```

1. **下载**：流式写入 `.part`，边下边算 SHA256；大小/哈希不符直接丢弃；
2. **暂存**：校验通过才解压到 staging；
3. **安装**：覆盖前写 journal；逐文件备份后覆盖；按清单删除"旧版本有、新版本没有"的文件；
4. **拉起**：detached 启动新版；
5. **探测**：3 秒内进程退出 → 判定失败 → 回滚并拉起旧版；
6. **清理**：删 staging/backup/下载缓存，客户端启动后清理 `*.old-*` 旧镜像。

## 8. 安装事务与"新包替换旧包"

不是简单覆盖，而是"覆盖 + 按清单删除"：

```
下载 zip → 解压 staging → 逐个覆盖（先备份）
→ 读上次清单 .update-files.json
→ 删除「旧清单有、新 staging 没有」的文件
→ 写回新清单
```

- 清单放在**安装目录的隐藏文件** `.update-files.json`（跟着程序走，清缓存也不会丢）；
- 旧版本（清单在缓存里）会自动迁移一次；
- 文件名带隐藏属性，资源管理器里默认不可见；
- `version.txt` 是普通包内文件，更新时被新包替换，**运行时不再单独写入**。

断电/崩溃用 `journal.json`：记录「目标文件 + 备份路径」，装完标 `committed`；
启动时 `--recover`（以及每次 `--check` 内部）发现未提交事务就按备份还原。

> 已知边缘：回滚会还原文件，但清单可能已是新的；下次更新只会删除"清单里有但实际不存在"的项，无副作用，最多少删一个旧文件。

## 9. 缓存与清理

```
%LOCALAPPDATA%\GenericUpdater\updates\<安装目录哈希>\
  ├── state.json       检查/跳过状态（长期保留）
  ├── staging/ backup/ 安装期间临时（成功后删）
  └── *.zip *.part     下载缓存（成功后删）
```

- 系统缓存不可写（受限账户/安全软件/沙箱）时回退 `<安装目录>\.app-update` 并打日志；
- 安装目录只留：程序 exe、`version.txt`、隐藏清单 `.update-files.json`。

## 10. 签名

- 信封：`{"schema":1,"keyId":"…","payload":"<base64>","signature":"<base64>"}`；
- 签名对象：payload 的**原始 UTF-8 字节**；
- 算法：RSA-PSS + SHA-256 + salt 32，密钥 3072 位；
- 公钥编译进 exe（`resources/update-trusted-keys.json`），私钥只存 GitHub Secret `UPDATE_SIGNING_KEY`；
- CI 有 secret 才签名；`require_signature=true` 时客户端拒绝明文/签名不符的 feed。

密钥只配一次。轮换：`keys` 数组追加新公钥（新 `id`）→ 发过渡版本 → 再移除旧公钥。

## 11. 进程协调与权限

| 场景 | 做法 |
|---|---|
| 等主程序退出 | `OpenProcess + WaitForSingleObject`（30s），拿不到句柄视为已退出 |
| exe 被占用 | 文件占用重试 90s 兜底 |
| 安装目录不可写 | `ShellExecuteW("runas")` 提权重启自身（带 `--elevated`） |
| 更新器自更新 | 运行中的 exe 先改名 `*.old-<pid>` 再写新文件，客户端启动后后台删除 |
| 重复启动 | 互斥体 + 重试，避免重启瞬间误判 |
| 新版起不来 | 3 秒存活探测失败 → 回滚 + 拉起旧版 |

## 12. 发布流水线

`.github/workflows/build.yml`：

1. 解析 tag → 版本号（`v0.6.0` → `0.6.0`）；
2. 校验签名配置（要求签名但没 secret / 有 secret 但公钥为空 → 直接失败）；
3. 编译 Rust 更新器与 C++ GUI（GUI 的版本号用 tag 注入）；
4. 打包 zip、算 SHA256、生成 `.sha256` 与 feed；
5. 从 `CHANGELOG.md` 抽取当前版本小节，写进 Release 正文和 `feed.notes`；
6. 有 secret 则签名 feed；
7. 上传 Release。

## 13. 与杀软/沙箱的关系

更新器天然具备"下载 → 替换 → 重启"的行为，容易被启发式标记。已做的降噪：

| 改动 | 目的 |
|---|---|
| 更新器改 GUI 子系统（`windows_subsystem="windows"`） | 不再产生"隐藏窗口子进程" |
| 客户端不再传 `CREATE_NO_WINDOW` | 同上 |
| 启动不再单独拉 `--recover` | 少一次隐藏进程 |
| 写文件改共享模式 | 去掉"独占方式打开文件" |
| 进度条只在可见性变化时切换 | 去掉多余"隐藏窗口" |
| 启动延迟 30s | 行为时间线更像正常程序 |
| 发布包不带 README.txt | 避免系统用记事本打开产生无关行为 |

仍未解决：**没有 Authenticode 代码签名**，SmartScreen 会提示未知发布者，部分引擎仍会报启发式（Avira/Bkav/Rising 尤其明显）。

## 14. 已知限制

- 不支持增量，每次整包下载；
- 没有 Authenticode 证书；
- 启动探测只看 3 秒内存活，之后崩溃不会自动回滚；
- 极端断电（journal 写一半）可能残留，需要 `--clean`；
- 平台只验证了 Windows x64；
- 若主程序是"启动即退出的启动器"，探测会误判，需要关掉探测或改成标记文件方案。
